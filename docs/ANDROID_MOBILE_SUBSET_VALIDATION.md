# Android rights-clear mobile subset validation

Validation date: 2026-09-02

This record separates physical-device observations, numerical comparison, and
claims that remain unproven.  It contains no device identifier, MediaStore URI,
raw tensor, APK, media file, log, or hash; those artifacts stay in ignored local
directories.

## Scope and controls

- Target: exactly one physical arm64 Qualcomm phone.  Emulator results are not
  included.
- App route: the Android QNN HTP benchmark intent, `SUSTAINED` tuning, with
  strict QNN configuration required and CPU EP fallback disabled.
- Inputs: the committed `mobile-rights-clear-subset-v1` contract materialized
  locally from the pinned open-asset manifest.  It has three quick-functional
  clips and eight core clips, covering 360p/480p/720p, 16:9 and pillarboxed
  square artwork, clean and blur-plus-JPEG degradations.
- Rights boundary: the subset is engineering coverage, not commercial anime.
  Big Buck Bunny cadence is generated by repeat/hold from 15 fps source frames,
  so its 24/30 fps containers are not evidence of native 24/30 fps motion.
- Publication boundary: media, receipts, APKs, device logs, tensors, PC outputs,
  and Lanczos images remain Git-ignored.  Only contracts, tooling, tests, and
  this sanitized report are source-controlled.

## Physical-device matrix result

Every standard run used the mandatory `720p-baseline -> 1080p-primary` order.
The clean reporting set contains no tensor capture request.  Across the 11
contract clips, all 22 standard reports were functional `PASS`, all were
classified `offline`, and none recorded a report-level failure or device error.

| Case group | Functional result | Performance classification | Measured frames | Observed fps |
| --- | --- | --- | ---: | ---: |
| 720p baseline, 11 clips | 11/11 PASS | offline | 645–835 (median 685) | 22.41–28.34 (median 23.71) |
| 1080p primary, 11 clips | 11/11 PASS | offline | 295–335 (median 315) | 10.70–11.96 (median 11.69) |
| 1440p experimental, gated after primary PASS | PASS | offline | 195 | 7.71 |
| 4K display fallback, gated after primary PASS | PASS | offline | 305 | 11.36 |

The 1080p primary median stage timings were queue p50/p95 329/348 ms, ORT
run p50/p95 43/47 ms, output conversion p50/p95 37/42 ms, and total processing
p50/p95 414/435 ms.  These are effect-pipeline samples, not SurfaceFlinger
latch, audio/video sync, end-to-end display latency, or NPU-kernel-only timing.

The named 4K case is explicitly a GPU display fallback from a 1080p neural
output.  It is not native 4K neural inference.

## QNN and numerical evidence

Each accepted QNN run carried the strict registration, NPU selection, provider
configuration, HTP backend, selected-NPU-count, and CPU-fallback-disabled
attestation required by `contracts/android-video-frame-golden-plan.json`.
This is session-configuration evidence only: it does **not** prove per-node
provider placement or provide a provider fallback trace.

For all contract-selected frames, the evidence set contains 27 comparisons:
one per quick clip and three per core clip (first, middle, and last contract
indices).  Every comparison passed the PC CPU numerical gate using the exact
Android-captured NCHW float32 input bytes: zero mismatches and zero nonfinite
values at the committed `atol=0.002`, `rtol=0.002` threshold.  A host Pillow
RGB8 Lanczos artifact was also generated for every selected frame.

This is an observed tensor comparison only.  It does not qualify frozen P4
real-image/SSIM requirements, full-frame/video/display quality, subjective
quality, or QNN node placement.

## Important repair and retained boundary

The first strict 1080p attempts stopped after a single 7.5-second quick clip
and collected only 75 measured frames, below the unchanged 120-frame
functional gate.  The cause was benchmark playback ending once rather than
filling the 30-second benchmark window.  The repair enables repeat-one only
for a valid benchmark intent and restores repeat-off for normal playback,
clear, and configuration-failure paths.  No performance threshold, warm-up
count, or numerical tolerance was weakened.

A later audit found that the then-permitted standard-matrix first-frame tensor
capture synchronously writes full tensors on the processing executor.  Its
outputs remain valid numerical evidence, but its timing reports are excluded
from this document.  The runner now rejects `-CaptureFrame` outside
`-CaptureOnly`; all 22 performance reports above were re-run without capture.

After that repair, all standard reports above passed their functional gate but
remained `offline`.  Therefore no realtime thermal/stability qualification was
run or claimed.  This is neither a thermal PASS nor a thermal FAIL; it is an
unmet precondition for a realtime thermal claim.

## Reproduction outline

Materialize and register a local-only controlled clip first.  The registration
receipt is ignored and binds the exact MediaStore item without committing its
URI.

```powershell
$receiptPath = '.\local-artifacts\mobile-subset\push-receipt-<clip>.json'
$receipt = Get-Content -Raw -LiteralPath $receiptPath | ConvertFrom-Json

.\scripts\run-android-qnn-resolution-matrix.ps1 `
  -ApkPath .\app\build\outputs\apk\debug\app-debug.apk `
  -VideoUri $receipt.mediaStoreUri `
  -MediaRegistrationReceipt $receiptPath
```

For every selected frame (including the first), only a matching 1080p
functional-PASS report may authorize capture-only evidence.  Standard matrices
reject `-CaptureFrame` so synchronous tensor writes cannot contaminate their
performance samples.  Capture-only intentionally produces no performance
claim.

```powershell
.\scripts\run-android-qnn-resolution-matrix.ps1 `
  -ApkPath .\app\build\outputs\apk\debug\app-debug.apk `
  -VideoUri $receipt.mediaStoreUri `
  -MediaRegistrationReceipt $receiptPath `
  -CaseId 1080p-primary `
  -CaptureOnly `
  -PrimaryReportPath <matching-ignored-1080p-report> `
  -CaptureFrame 91
```

Pull app-private evidence and compare it only under an ignored evidence root:

```powershell
.\scripts\pull-android-video-frame-evidence.ps1 -RunId <captured-run-id>

& .\build\fixed512-python-env\Scripts\python.exe `
  .\golden-correctness\compare_android_video_frame.py `
  --evidence-dir .\device-results\android-video-evidence\<captured-run-id> `
  --model .\derived-models\quicksrnet-small-3x-fixed640x360.onnx `
  --output .\device-results\android-video-evidence\<captured-run-id>\pc-comparison
```

The runner rejects emulators, non-arm64 targets, unbound media, a direct
1080p bypass, and experimental 1440p/4K cases without a matching primary
functional PASS report.
